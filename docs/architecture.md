# 谁是卧底应用架构

当前应用由 UnderCover 前端（Vue 和 TypeScript）、UnderCover 服务端、灵矽智能体三部分协作完成。**UnderCover 前端负责交互和声音呈现，UnderCover 服务端保存真实游戏状态并执行规则，灵矽负责听懂玩家、扮演 AI 玩家和生成语音。** 灵矽通过调用 UnderCover 服务端提供的游戏工具执行操作；发牌、投票和胜负以 UnderCover 服务端的执行结果为准。

本文对应已接入灵矽的正式游戏模式。未配置灵矽时，应用使用页面标识的本地演示策略。UnderCover 前端经 Vite 构建后通过 `go:embed` 嵌入 UnderCover 服务端，浏览器从同一个应用域名加载页面和访问 API。

## 三方职责

| 组件 | 负责的事情 | 保存或处理的数据 |
| --- | --- | --- |
| UnderCover 前端 | 展示大厅、圆桌和词卡；采集麦克风；提交按钮或文字操作；接收房间事件；播放音频并同步头像气泡 | 当前账号可见的房间快照、自己的词、播放队列和播放进度 |
| UnderCover 服务端 | XBuilder 登录和会话；房间与座位；随机发牌；发言顺序、计票、淘汰及胜负；提供 MCP 工具；转发语音并缓存音频 | 完整对局、全部词卡与身份、会话哈希、公开发言记录、内存音频 |
| 灵矽 | 语音识别；理解“开始游戏”“我的描述”“我投二号”等意图；调用游戏工具；生成 AI 描述与投票；主持和语音合成 | UnderCover 服务端提供的房间上下文、AI 任务、当前语音会话上下文 |

XBuilder 是登录依赖。浏览器经授权流程登录，UnderCover 服务端完成令牌交换并建立 Redis 会话；游戏请求携带应用会话 Cookie。灵矽设备 Token、XBuilder Client Secret 都保留在 UnderCover 服务端。

### 建立会话与上传语音

UnderCover 前端先通过 `GET /api/rooms/{id}/events` 建立长期 SSE 订阅。SSE 是后端向浏览器推送房间状态的通道，各成员收到自己的房间视图，`myWord` 只包含自己的词。

玩家按住中央按钮后，UnderCover 前端连接 `/api/rooms/{id}/assistant/voice`。UnderCover 服务端校验登录和房间成员身份，取得该房间的主持占用权，将 `agentActive` 设为 `true`，在处理期间暂停对应回合的超时推进。

UnderCover 服务端以已绑定的软件终端身份接入灵矽。默认先通过 OTA 获取终端 Token 与连接地址，再建立服务端 WSS 连接，发送公开房间上下文和主持约束。灵矽通过 MCP 的 `initialize`、`tools/list` 发现 UnderCover 服务端提供的游戏工具。

浏览器取得麦克风后立即录音，上游连接期间缓存在本机；UnderCover 服务端返回 `ready` 后按顺序发送已录制的与后续 PCM。音频为 16 kHz、单声道 PCM16LE，通常每 20 ms 发送 640 字节。UnderCover 服务端将音频转发给灵矽。玩家松开按钮，UnderCover 前端发送 `stop`，UnderCover 服务端再向灵矽发送 `listen.stop`。灵矽返回识别文本时，UnderCover 服务端转为 `transcript` 发给UnderCover 前端；此时对话继续，尚未结束。

### 灵矽调用工具推进游戏

灵矽结合注入的当前上下文和识别原文选择工具，仅在状态不明或用户询问时查询 `game.get_state`。真人描述通过 `game.submit_description` 提交，UnderCover 服务端优先使用本次 STT 原文，校验发言顺序与词语后保存文字和原声。

每次会话成功执行一个游戏动作就结束工具推进。描述阶段的 `game.get_ai_batch` 只包含一位 AI，灵矽生成并提交这一位的描述；UnderCover 服务端使用当前任务 ID 和游戏副本校验顺序、合法性，再原子保存。AI 投票仍可整组提交，且要等所有存活真人投完后才发出任务。后续 AI 描述由后台另行触发，不等待多位 AI 都提交后再汇总播报。

### 返回声音并同步界面

每次提交立即推送 SSE，所有成员把公开记录放进同一个播放队列，包括发言本人。真人提交的原声可直接通过音频接口获取并播放；纯文字发言和 AI 描述由灵矽合成。当前玩家的发言播完后，才播放下一位提示。

UnderCover 服务端中断模型在工具调用后的自由总结，复用当前灵矽连接，以 `listen.detect` 的 `text_response` 指定本次已提交的公开文本。只缓存句子文本与该条记录一致的 TTS，忽略中断前残留的模型音频。每条音频按原发言记录 ID 独立缓存，不追加一条包含内部分析的主持总结。

UnderCover 前端通过 `GET /api/rooms/{id}/audio/{event}` 获取本条声音。若 SSE 先于 TTS 到达，HTTP 请求等待对应缓存，不为同一条记录另抢设备连接。该条音频就绪即可播放；不等待整组 AI。头像气泡、发言列表及高亮跟随本机播放时钟。会话最后返回 `assistant_done` 并释放房间占用权，后台再处理下一位 AI。

没有执行游戏动作的查询也不转发模型自由回复。UnderCover 服务端根据真实当前座位生成中文状态提示，规则查询采用权威规则文本，并由灵矽合成；原始模型文字和音频均不缓存、不广播。真人会话不提供AI回合工具，玩家名字和身份仅来自当前房间。

## 开局与投票入口

同一个规则引擎处理语音工具和网页按钮。正式游戏的开局与再次开局通过语音发起；文字描述、点击投票仍保留直接操作入口。未配置灵矽的体验模式提供开局按钮。

| 玩家操作 | 入口与灵矽行为 | UnderCover 服务端的执行结果 |
| --- | --- | --- |
| 说“开始游戏” | 灵矽理解意图，调用 `game.start` | 校验房主；补齐 AI 座位；随机分配词和卧底；发牌后进入描述阶段 |
| 体验模式点击“开始体验” | 未配置灵矽时，UnderCover 前端请求 `POST /start` | 执行开局规则，SSE 同步词卡与阶段；AI 使用本地演示策略 |
| 按住描述自己的词 | 灵矽调用 `game.submit_description` | 保存描述和原声，先播本次发言，再提示下一位 |
| 输入文字并确认 | UnderCover 前端直接请求 `POST /speech` | 保存描述；有待处理 AI 时由后台调度灵矽接续 |
| 说“我投二号” | 灵矽调用 `game.vote` | 校验阶段、身份、是否已投和合法目标；票齐后统一计票 |
| 点击玩家后确认投票 | UnderCover 前端直接请求 `POST /vote` | 执行同一套投票规则；需要 AI 投票时调度灵矽 |
| 说“跳过”或点击跳过 | `game.skip` 或 `POST /skip` | 跳过自己的发言，不伪造一条玩家描述 |

表中的 HTTP 路径省略了 `/api/rooms/{id}` 前缀。票齐后，UnderCover 服务端决定淘汰、平票加赛、进入下一轮或结束。结束时，房间视图才包含所有人的 `reveals`，UnderCover 前端翻开桌面词卡并展示胜负；灵矽根据规则执行结果播报。

### 没有麦克风输入时如何触发 AI

按钮或文字操作成功后，UnderCover 服务端每 500 ms 检查待处理的 AI 任务。需要 AI 行动时，后台取得房间主持占用权，用缓存的“继续主持”语音进入同一套灵矽语音和 MCP 会话。该短音频首次由灵矽合成，转换为 16 kHz PCM 后供后续调用复用。

因此，当前自动接续也使用绑定的灵矽智能体，**不读取 `LLM_BASE_URL`、`LLM_API_KEY` 或 `LLM_MODEL`**。UnderCover 服务端负责触发时机与工具执行，AI 内容仍由灵矽生成。有真人正在发言、或正在等待真人投票时，不会提前生成对应 AI 任务。

## 通信与语音同步

| 通道 | 方向 | 承载内容 |
| --- | --- | --- |
| HTTP JSON | UnderCover 前端与 UnderCover 服务端 | 登录状态、大厅、入座、开始、文字发言、点击投票 |
| SSE | UnderCover 服务端 → UnderCover 前端 | 个性化 `RoomView`、阶段、公开记录、`agentActive`、状态版本 |
| 浏览器 WebSocket | UnderCover 前端 ↔ UnderCover 服务端 | 本次麦克风 PCM、停止指令、识别文本、识别结果与控制消息 |
| 服务端 WSS | UnderCover 服务端 ↔ 灵矽 | 设备语音协议、提示词上下文、MCP JSON-RPC、ASR 与 TTS |
| HTTP 音频 | UnderCover 服务端 → UnderCover 前端 | 公开录音、缓存的灵矽原声，或按公开记录重新合成的音频 |

MCP 工具调用与语音共用 UnderCover 服务端到灵矽的 WSS 连接。当前 UnderCover 服务端直接实现端侧 MCP 协议，没有单独部署一个公网 MCP 服务。UnderCover 前端也不直接连接灵矽。

完整音频的 `audioCues` 保存逐句播放标记，例如：

```json
{
  "offsetMs": 3200,
  "text": "它在生活里经常出现。",
  "logId": "speech-example",
  "playerId": "player-example",
  "seat": 2
}
```

所有新播报都按记录排队，按媒体的 `currentTime` 选择当前发言。旧版缓存音频仍可按 `offsetMs` 选择句子。网络收到下一句文字，不会立即切换头像气泡。成功游戏动作使用按记录去重的单队列播放；查询回复也使用同一条记录，不另行播放模型原始音频。

这保证的是单个浏览器内的文字与声音同步。不同成员的网络、自动播放权限和播放进度可能不同，目前没有统一的跨客户端播放时钟。音频缓存丢失后重新合成的声音，逐句时长也可能与原始标记不同。

## 状态管理与异常处理

识别后未提交的真人发言按游戏ID、轮次、阶段和玩家ID绑定为私密草稿，只有本人的视图包含 `myDraft`，同时暂停该回合的超时跳过；确认提交后清除。草稿文字持久化，录音在内存中；重连或重启可以恢复文字继续确认。普通查询不作为玩家描述，语音跳过必须明确表达。

UnderCover 服务端的房间管理器和规则引擎保存完整状态；浏览器和灵矽都通过受限接口访问。PostgreSQL 的 `undercover_rooms.state` JSONB 持久化每间房间的完整状态，UnderCover 服务端通过 pq 驱动按房间写入；Redis 保存以随机 Token 哈希为键的用户会话并设置七天 TTL。应用不再读写 `data` 目录。音频、SSE 订阅和计时器仍保留在内存，部署方式为单实例，PostgreSQL advisory lock 阻止同一 schema 同时运行两个游戏进程。

房主确认关闭后，UnderCover 服务端先删除 PostgreSQL 记录，成功后清除内存状态、取消正在进行的语音与 AI 处理，并发送 `closed` SSE。所有成员停止播放并回到大厅；大厅后续刷新不再显示该房间。删除或写入失败时保留原状态，避免界面显示成功而数据库未保存。空数据库不会自动生成演示房间，关闭后的房间不会在重启时重新出现。

- **词卡隔离**：结束前，成员视图只返回自己的词。主持公开上下文去掉真人词卡，AI 任务单独把待行动 AI 的词交给灵矽。公开主播播报若命中尚未揭晓的完整词语，会被替换为安全提醒。
- **AI 角色边界**：同一个灵矽主持会话扮演多个 AI；一个任务组可能包含多位 AI 的词。当前没有为每位 AI 建立独立模型上下文，不能把提示词中的角色约束理解为严格的信息隔离。
- **操作校验**：工具绑定当前登录账号与房间，拒绝越权、乱序和非法投票。同一语音会话内缓存相同 MCP 请求的结果，避免传输重试重复执行；这不是跨连接的全局幂等机制。
- **会话占用**：同一房间只允许一个主持会话，处理期间暂停回合超时。单个软件终端同时只承载一条上游语音连接，多个房间并行需要足够的终端身份。
- **云端失败**：仍待处理的 AI 回合会退避重试；已经通过校验提交的操作保留。若该条 TTS 中断，队列按原公开记录重试合成，不能生成另一段描述。配置了灵矽时，不会悄悄切到本地演示机器人生成 AI 行动。
- **播放失败**：浏览器阻止自动播放时保留队列并提示点击开启声音；灵矽音频获取失败时尝试浏览器语音并显示来源。历史房间恢复后不自动重播整局。
